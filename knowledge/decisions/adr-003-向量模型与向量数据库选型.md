# ADR-003：向量模型与向量数据库选型

> 范围：文本向量模型、图片（架构图 / ER 图）向量模型、向量数据库的选型依据，以及向量检索的底层原理。
> 读者：要判断"为什么这么选""换模型/换库要付什么代价""检索效果不好该调哪里"的实现者与维护者。

---

## 0. 结论速览

| 决策项 | 结论 | 一句话理由 |
|---|---|---|
| 文本向量（本地默认） | `BAAI/bge-m3`，1024 维 | 中文强、8k 上下文、免指令前缀、中英混排稳 |
| 文本向量（低配兜底） | `BAAI/bge-small-zh-v1.5`，512 维 | 约 95MB，CPU 上快一个量级，短块质量够用 |
| 文本向量（线上） | `text-embedding-3-small` / 阿里 `text-embedding-v3` | 零本地依赖、按量付费，适合不想装 ML 运行时的机器 |
| 图片向量 | `OFA-Sys/chinese-clip-vit-base-patch16`，512 维 | 中文场景的 CLIP 双塔，可文本搜图、图搜图 |
| 向量数据库 | LanceDB（嵌入式） | 零服务、列式 + 版本化、过滤与向量同查询 |
| 元数据 / 队列 | SQLite（WAL） | 单文件事务，与向量库解耦 |
| 检索融合 | 向量 + BM25 + RRF | 纯语义会漂移字段名，纯字面会漏同义改写 |

选型不是"谁榜单最高"，而是"在**单机 + 内嵌 + 可离线 + 按需安装**的约束下，总体代价最低"。

---

## 1. 约束条件

1. **单机、零运维**：MCP 是常驻本地的单进程，不能要求用户额外起 Docker、PG、Milvus。
2. **可离线**：内网环境不能假设一定能调外部 embedding API。
3. **基础安装必须轻**：不用向量功能时不安装 torch 等机器学习依赖。
4. **中文技术文档为主**：大量中英混排（中文描述 + 英文表名/字段名/接口名）。
5. **需要元数据过滤**：按 `kb_id`、目录前缀、`doc_type`、`status`、`authority` 先裁剪候选集。
6. **需要图片检索**：架构图、ER 图、流程图承载"关系"，仅靠 alt 文本检索会落空。
7. **文档会持续变**：增量索引、整篇替换、删除都要便宜且幂等。

## 2. 向量是什么

### 2.1 一句话定义

**向量（embedding）是把一段内容映射成固定长度的浮点数组，使"语义相近"的内容在空间中距离更近。** 模型只做这一件事：`text -> [f1, f2, ..., fd]`。相似度计算、存储、召回都是在其上叠加的工程。

### 2.2 相似度度量

| 度量 | 公式 | 特点 | 本项目 |
|---|---|---|---|
| 余弦相似度 | `cos(a,b) = a·b / (|a||b|)` | 只看方向，对长度不敏感 | 使用（`metric("cosine")`） |
| 内积 | `a·b` | 计算最快，但受向量模长影响 | 归一化后与余弦等价 |
| 欧氏距离 | `‖a-b‖` | 对绝对位置敏感 | 不使用 |

工程上统一做 **L2 归一化**（`normalize_embeddings=True`），于是余弦、内积、欧氏三者单调等价，后续换索引类型不会改变排序语义。

### 2.3 维度意味着什么

维度不是越高越准。它决定：表达能力上限、单条存储成本（`d × 4` 字节）、检索计算量。1024 维 `float32` 约 4KB/条，10 万条约 400MB；用 PQ 量化后可压到几十 MB。

### 2.4 上下文窗口与分块

模型有最大输入长度（512 / 8192 / 32k token 不等），超出会被截断，**截断意味着信息直接丢失**。因此长文档必须切块：

- 块太大：一个向量混了多个主题，检索粒度粗、命中后还得再定位。
- 块太小：上下文断裂，"它""该字段"这类指代失去含义。
- 本项目取 **512 token、重叠 64**；表格、代码块、图片例外（见架构文档 3.5）。

### 2.5 为什么必须混合检索

向量擅长"意思一样但字不一样"，不擅长精确 token：

| 查询 | 向量检索 | BM25 |
|---|---|---|
| "订单状态怎么流转" vs 正文"订单生命周期" | 命中 | 可能漏 |
| `so_id` 字段名 | 容易被语义漂移掉 | 精确命中 |
| 错误码 `E1024` | 几乎必错 | 精确命中 |

所以检索链路是 **向量召回 + BM25 召回 + RRF 融合**，而不是"上向量就够了"。

## 3. 向量数据库原理

### 3.1 为什么需要专门的数据库

最朴素的检索是暴力扫描：对 N 条向量逐条算余弦，复杂度 `O(N·d)`。

- 1 万条 × 1024 维：单次约 1000 万次乘加，毫秒级，**根本不需要索引**。
- 100 万条 × 1024 维：约 10 亿次乘加，单次百毫秒级，必须上 ANN。

所以"小库用精确扫描、大库用近似索引"是合理策略，不是妥协。**本项目当前就是精确扫描**（`kb_<kb_id>` 表未建 ANN 索引），几万块规模下召回率 100%，不存在近似误差。

### 3.2 ANN 的四类思路

| 类型 | 代表 | 核心思想 | 代价 |
|---|---|---|---|
| 树 | KD-Tree、Ball-Tree | 空间递归切分 | 高维退化，几乎不用于向量 |
| 哈希 | LSH | 相似向量以高概率落同一桶 | 召回率不稳，参数难调 |
| 图 | **HNSW** | 近邻图 + 分层跳表式贪心搜索 | 内存大、构建慢、删除麻烦 |
| 量化 | **IVF / PQ / SQ** | 先聚类缩小范围，再压缩向量降算力 | 有精度损失，需要训练码本 |

### 3.3 HNSW

把每条向量作为图节点，连向若干近邻；上层稀疏用于快速跳转，底层稠密用于精细搜索。查询从顶层入口点贪心走向更近的邻居，逐层下沉。

- 参数：`M`（每层邻居数）、`efConstruction`（建图搜索宽度）、`efSearch`（查询搜索宽度）。
- 优点：高召回、低延迟；缺点：**全内存**，百万级就很吃内存，删除靠标记。

### 3.4 IVF + PQ（LanceDB 的默认组合）

**IVF（倒排文件）**：先对所有向量做 k-means，得到 `nlist` 个簇心；每个向量归入最近簇，形成倒排表。查询时只探测最近的 `nprobe` 个簇。复杂度从 `O(N)` 降到约 `O(N·nprobe/nlist)`。

**PQ（乘积量化）**：把 `d` 维向量切成 `m` 段，每段用 256 个码字（1 byte）的码本表示。1024 维 `float32`（4KB）可压到 128 字节，内存降 32 倍。距离用查表累加（ADC，非对称距离）近似。

**组合效果**：IVF 缩小候选范围，PQ 降低单次距离计算成本。代价是 `nprobe` 太小会漏召回、`m` 太大会失真。

**取舍**：小库不要建索引（精确扫描更快更准）；十万级以上再建 `IVF_PQ`，并用固定查询集对比"索引召回率 / 精确结果"验证精度损失。

### 3.5 过滤：pre-filter 与 post-filter

带元数据条件时有两种做法：

- **post-filter**：先取 Top-K 向量，再按条件过滤。条件越严格，结果越少，常见"过滤后只剩 1 条"。
- **pre-filter**：先用条件裁剪出候选集，再在候选集内做向量检索。

本项目用 `where(...).prefilter=True`（见 [store.py](../../kb_gateway/store.py)），因为 `prefixes` 与 `authority` 是硬性授权边界，绝不能靠"取回来再筛"。

### 3.6 写入、删除与版本

LanceDB 的底层是 Lance 列式格式：

- 每次写入生成新的 `fragment` 数据文件，并写入新的 `manifest`（版本快照）。
- 删除先写 deletion 标记（逻辑删除），之后由 compaction 合并文件真正回收空间。
- 因此 `delete + add` 的"整篇替换"很便宜，且旧版本仍可读（时间旅行）。

**运维注意**：频繁 upsert 会产生大量小文件，需定期 compact，否则扫描变慢。

## 4. 文本向量模型选型

### 4.1 评价维度

| 维度 | 为什么重要 |
|---|---|
| 中文 / 中英混排效果 | 语料是中文技术文档，英文只出现在标识符里 |
| 上下文长度 | 决定表格、长章节会不会被截断 |
| 是否要求指令前缀 | 当前编码器对 query / passage 用同一套编码，非对称模型会掉点 |
| 维度 | 影响存储与算力，且换维度必须重建索引 |
| 运行成本 | CPU 吞吐、内存占用、是否需要 GPU |
| 可离线 / 许可 | 内网可用性、商用限制 |
| 榜单表现 | MTEB / C-MTEB 只能作参考，最终要拿自己的语料验证 |

### 4.2 候选对比

| 模型 | 维度 | 上下文 | 中文 | 部署 | 结论 |
|---|---|---|---|---|---|
| **BAAI/bge-m3** | 1024 | 8192 | 强 | 本地，约 2.3GB | **本地默认** |
| BAAI/bge-small-zh-v1.5 | 512 | 512 | 强 | 本地，约 95MB | 低配兜底 |
| BAAI/bge-base-zh-v1.5 | 768 | 512 | 强 | 本地，约 400MB | 质量/体积折中 |
| BAAI/bge-large-zh-v1.5 | 1024 | 512 | 很强 | 本地，约 1.3GB | CPU 上偏慢 |
| Qwen3-Embedding-0.6B | 1024 | 32k | 很强 | 本地，需较新依赖 | 效果优先可选 |
| multilingual-e5-base | 768 | 512 | 中 | 本地 | 需 `query:` / `passage:` 前缀，不选 |
| text-embedding-3-small | 1536 | 8191 | 中上 | 线上 | 线上默认 |
| text-embedding-3-large | 3072 | 8191 | 上 | 线上 | 成本高、维度大 |
| 阿里 text-embedding-v3 | 1024 | 8192 | 很强 | 线上 | 国内线上优选 |
| jina-embeddings-v3 | 1024 | 8192 | 强 | 线上/本地 | 依赖 task LoRA 参数，不选 |

> 参数量与内存为量级估算，以模型卡为准。

### 4.3 为什么默认 bge-m3

1. **免指令前缀**：query 与正文同构编码即可用，与现有 `LocalEmbedder` 的实现完全对齐。
2. **8192 上下文**：中文技术章节、跨行表格不会在 512 处被硬截断。
3. **中英混排稳**：中文语义 + 英文标识符共存时，不会因为语言切换导致向量漂移。
4. **稠密向量直出**：不需要额外拼稀疏/多向量，工程复杂度最低。
5. **可离线、可固定 revision**：满足内网与可复现要求。

### 4.4 为什么不选"榜单更高"的模型

- **e5 系列**：训练目标是非对称检索，必须给 query 加 `query: `、给正文加 `passage: `。当前编码链路不注入前缀，效果会明显低于榜单。
- **jina-v3**：依赖 `task` 参数切换 LoRA，同样属于"调用方式有契约"的模型。
- **超大模型 / 多向量模型**：检索质量提升有限，但 CPU 延迟与内存代价翻倍，还会拖慢索引队列。

如果将来要做"指令感知编码"，正确做法是给 `EmbeddingProfile` 增加 `query_prefix` / `passage_prefix` 字段，而不是换一个模型却沿用旧调用方式。

### 4.5 切换模型的代价

维度写死在 LanceDB 表结构里，切换模型必须：

1. 新 profile 产生新的 `model_generation`；
2. 全量重建到新代次表，期间旧代次继续服务；
3. 校验新代次 `doc_count / chunk_count` 与抽样检索结果；
4. 原子切换并清理旧代次。

**不能"就地增量"**，否则同一张表里会混入不同维度或不同语义空间的向量，检索结果不可解释。

## 5. 向量数据库选型

### 5.1 候选对比

| 方案 | 部署形态 | 元数据过滤 | CRUD | 持久化 | 多模态 | 运维成本 | 结论 |
|---|---|---|---|---|---|---|---|
| **LanceDB** | 嵌入式库 | 支持，可 prefilter | 支持 | 列式文件 | 类型无关 | 极低 | **选用** |
| Chroma | 嵌入式/服务 | 支持，较弱 | 支持 | SQLite+文件 | 文本为主 | 低 | 并发写弱 |
| FAISS | 纯索引库 | 无 | 无 | 需自己序列化 | 类型无关 | 中（全自研） | 不适合 |
| Qdrant | 独立服务 | 强 | 强 | 自管理 | 支持 | 中高 | 规模大时再考虑 |
| Milvus | 独立集群 | 强 | 强 | 依赖 etcd/对象存储 | 支持 | 高 | 过重 |
| pgvector | PG 扩展 | 强（SQL） | 强 | PG | 支持 | 中（要 PG） | 已有 PG 时可选 |
| sqlite-vec | SQLite 扩展 | 弱 | 弱 | SQLite | 支持 | 极低 | 生态不成熟 |
| ES / OpenSearch | 独立服务 | 很强 | 强 | 自管理 | 支持 | 高 | 过重 |
| Redis Stack | 独立服务 | 中 | 强 | 内存为主 | 支持 | 中 | 持久化语义弱 |

### 5.2 为什么选 LanceDB

1. **嵌入式**：一个目录即数据库，随进程启动，无端口、无守护进程、无容器。
2. **列式 + Arrow 原生**：schema 直接用 pyarrow 定义，行数据就是 dict，无 ORM。
3. **过滤与向量同查询**：`where + prefilter` 一次完成授权裁剪与检索。
4. **版本化写入**：manifest 快照支持回溯与原子发布，适合"代次切换"。
5. **多表并存**：每 kb 一张文本表 + 一张图片表，维度互不影响。
6. **可迁移**：封装层薄（一个 `VectorStore` 类），真要换库成本可控。

### 5.3 已知代价

| 代价 | 表现 | 缓解 |
|---|---|---|
| 默认不建 ANN 索引 | 大库全量扫描慢 | 十万级后建 `IVF_PQ`，用固定查询集验证召回 |
| 逻辑删除 + 小文件 | 长期 upsert 后扫描变慢 | 定期 compact |
| 写入非事务 | 跨表写入不能原子化 | 双表各自幂等按 `doc_id` 替换，失败重试 |
| 生态较年轻 | API 偶有变动 | 锁定版本，封装层隔离 |
| 单机上限 | 百万级后吃力 | 到规模阈值换 Qdrant / Milvus |

### 5.4 什么时候该换库

- 向量规模 > 100 万，或需要多机 / 只读副本；
- 需要多租户、细粒度权限、原生混合检索与重排；
- 需要强事务与 SQL 生态（此时优先评估 pgvector 而不是新库）。

换库只影响 `store.py` 与 `search` 层，不应影响 MCP 工具契约。

## 6. 图片向量（架构图 / ER 图）

### 6.1 双塔模型与共享空间

CLIP 类模型由两个编码器组成：

- **图像塔**：`image -> image_vec`
- **文本塔**：`text -> text_vec`
- 训练时用对比学习把"匹配的图文对"拉近、不匹配的推远，使两者落在**同一个向量空间**。

于是可以直接比较 `text_vec` 与 `image_vec` 的余弦相似度，实现**文本搜图**；两条图片向量之间比较则实现**图搜图**。

关键前提：**查询与入库必须用同一个模型**。用 A 模型编码图片、B 模型编码文本，两个空间毫无关系，检索结果等于随机。

### 6.2 为什么用双塔而不是 VLM 生成描述

| 方案 | 优点 | 缺点 |
|---|---|---|
| **CLIP 双塔** | 快、便宜、可离线、可图搜图 | 不理解图内文字与细节结构 |
| VLM 生成 caption | 能用自然语言描述复杂结构 | 慢、贵、可能幻觉、长图易漏 |

结论：**双塔做召回，caption 做兜底**。ER 图里的表名、字段名这类精确信息，靠人工 alt 文本或 OCR 补足，而不是指望 CLIP 认字。

### 6.3 图片模型候选

| 模型 | 维度 | 说明 |
|---|---|---|
| **OFA-Sys/chinese-clip-vit-base-patch16** | 512 | 中文语料训练，架构图/ER 图场景默认 |
| OFA-Sys/chinese-clip-vit-large-patch14 | 768 | 质量更高，CPU 更慢 |
| SigLIP base/384 | 768 | 英文场景更强，中文一般 |
| openai/clip-vit-base-patch32 | 512 | 通用基线，中文偏弱 |

### 6.4 存储与检索

- **独立表**：`kb_<kb_id>__img`，与文本表物理分离。原因是维度不同（512 vs 1024），而 LanceDB 的向量列建表即固定维度。
- **文本搜图**：`query` 用同一模型的**文本塔**编码 → 在图片表做余弦检索。
- **图搜图**：图像塔编码 → 同表检索。
- **结果融合**：图片命中与文本命中一起进 RRF，图片项标 `kind=image`，返回 `caption` 与路径，不返回二进制。
- **去重**：按 `image_hash` 去重，多文档引用共享同一向量行。

### 6.5 局限与补偿

| 局限 | 补偿手段 |
|---|---|
| 认不出小字、字段名 | 规范要求 alt 文本写出核心实体；可选 OCR 结果进 BM25 |
| 长宽比极端（超宽流程图） | 入库前限制长边并补白，避免缩放后细节糊掉 |
| 相似图互相挤占 Top-K | 按文档去重，同一文档最多返回 N 张 |
| 模型对示意图 / 线框图不敏感 | caption + 标题路径加权，必要时引入重排模型 |

## 7. 容量与参数

| 参数 | 取值 | 依据 |
|---|---|---|
| 文本分块 | 512 token / 重叠 64 | 技术文档甜点区 |
| 文本向量维度 | 1024（bge-m3） | 质量与成本平衡 |
| 图片向量维度 | 512（Chinese-CLIP B/16） | 中文场景默认 |
| 图片长边 | ≤ 2048，最小 224 | 兼顾小字可读与编码耗时 |
| 向量召回宽度 | `top_k × 3` | 给 RRF 留融合空间 |
| RRF 常数 | 60 | 通用经验值 |
| 建 ANN 索引阈值 | 单表 > 10 万块 | 低于此精确扫描更快更准 |
| 本地编码吞吐 | 20~40 块/秒（CPU，bge-m3） | 全量 1 万块约 4~8 分钟 |

存储估算：1024 维 `float32` 约 4KB/条，10 万条约 400MB；512 维图片向量约 2KB/条，1 万张约 20MB。

## 8. 演进路线

1. **现在**：精确扫描 + 文本/图片双表 + RRF。
2. **规模上来**：文本表建 `IVF_PQ`，定期 compact；用固定查询集对比召回率。
3. **质量不够**：在 RRF 之后加 cross-encoder 重排（如 `bge-reranker-v2-m3`），只对 Top-50 重排。
4. **图表检索不足**：加 OCR 通道，把图内字段名进 BM25；或对关键图调用 VLM 生成结构化 caption。
5. **多模态扩展**：同一双塔空间内可继续纳入截图、UI 稿；仍遵循"一个模态一张表"的维度解耦原则。
